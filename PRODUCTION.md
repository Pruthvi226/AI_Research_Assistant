# Deployment And Security Guide

The application now has native email/password accounts and owner-scoped API
access. This is a locally testable foundation, not a claim that the current
Render free service is durable or ready for sensitive production research.

## Current Runtime

- Frontend: React static build served by Nginx.
- Backend: Flask served by Waitress.
- Persistence: SQLite WAL; Docker Compose uses a named volume. The Render free
  configuration below is explicitly ephemeral.
- Retrieval: CPU-light hybrid BM25 with bounded research-domain term expansion by default; optional dense FAISS/sentence-transformer embeddings are not enabled on Render Free.
- Jobs: bounded in-process thread pool for async PDF processing.
- Observability: request IDs, response-time headers, health/readiness/metrics endpoints.
- Authentication: per-account password hashes and opaque, expiring bearer
  sessions; resource ownership is enforced in SQLite queries.

## Environment Configuration

Create a `.env` file from `.env.example` and set production values:

```env
APP_NAME=Scientia.ai
APP_VERSION=1.0.0
ENVIRONMENT=production
SECRET_KEY=replace_with_a_strong_secret
CORS_ORIGINS=https://your-frontend.example.com
GEMINI_API_KEY=your_gemini_api_key_here
GITHUB_TOKEN=your_optional_github_token_here
DATABASE_URL=sqlite:////app/data/scientia.db
RATE_LIMIT_PER_MINUTE=120
RATE_LIMIT_WINDOW_SECONDS=60
AUTH_RATE_LIMIT_PER_MINUTE=10
AUTH_SESSION_TTL_SECONDS=604800
JOB_WORKERS=3
JOB_MAX_IN_FLIGHT=50
JOB_RETENTION_LIMIT=500
MAX_UPLOAD_MB=50
```

## Deploy With Docker Compose

```bash
docker-compose up --build -d
```

Health checks:

```bash
curl http://localhost:5000/api/health
curl http://localhost:5000/api/system/readiness
curl http://localhost:5000/api/system/metrics
```

## Operational Endpoints

| Endpoint | Purpose |
| --- | --- |
| `GET /api/health` | Backward-compatible health plus dependency snapshot. |
| `GET /api/system/health` | Detailed dependency, SLO, and scale-limit snapshot. |
| `GET /api/system/readiness` | Returns `503` when database or storage is unavailable. |
| `GET /api/system/metrics` | Queue, rate limiter, and retrieval counters. |

Every response includes `X-Request-ID` and `X-Response-Time-ms`. Propagate `X-Request-ID` from the frontend or API gateway when debugging user reports.

## Security Hardening Checklist

- Keep runtime secrets out of source control; `SECRET_KEY` is generated by the
  Render start command when not explicitly configured.
- Restrict `CORS_ORIGINS` to your deployed frontend domain.
- Terminate TLS at a reverse proxy, cloud load balancer, or CDN.
- All API routes that handle documents, chat/history, outputs, jobs, files, or
  settings require a bearer token. `/api/health`, `/api/system/health`, and
  `/api/system/readiness` remain public for platform health checks.
- Passwords are hashed server-side; raw bearer tokens are not stored in the
  database. The frontend keeps the active token in `sessionStorage` and clears
  it on sign-out or an expired-session response.
- Local accounts do not yet have email verification, password reset, MFA, or
  account recovery. Add an approved identity provider or those recovery
  controls before treating this as a production identity system.
- Existing documents without an owner are not assigned to the first account.
  They remain inaccessible until an operator performs a reviewed ownership
  migration.
- Store uploads and generated artifacts on encrypted storage.
- Rotate Gemini/GitHub tokens and prefer provider-side least-privilege controls.
- Add malware scanning if accepting untrusted PDFs from public users.

## GitHub Pages + Render

The Pages workflow reads the non-secret repository variable
`REACT_APP_API_URL` at build time. Set it to the HTTPS origin of the authorized
Flask service (for example, `https://your-service.onrender.com`) and set backend
`CORS_ORIGINS` to the Pages origin (for example,
`https://your-account.github.io`). The frontend variable is public configuration,
not a place for API keys or bearer tokens. The Pages workflow builds and
publishes the static frontend; the backend and its secrets are configured
separately in Render.

`render.yaml` remains a free/demo service definition with ephemeral storage.
SQLite account/document records, uploaded files, generated outputs, and in-memory
jobs can be lost when the service restarts or sleeps. Do not use this deployment
for private or irreplaceable material. A production release still requires an
approved durable database, persistent file/object storage, restart-safe job
queue, backup/restore policy, email verification or an identity provider, and
host-owner configuration. This repository change does not provision or deploy
any cloud resource.

## Capacity And Backpressure

- `RATE_LIMIT_PER_MINUTE` and `RATE_LIMIT_WINDOW_SECONDS` limit API bursts per caller key.
- `JOB_WORKERS` controls concurrent background work.
- `JOB_MAX_IN_FLIGHT` caps queued plus running jobs; saturated async upload returns `429 job_queue_full`.
- `JOB_RETENTION_LIMIT` bounds retained job metadata.
- `MAX_UPLOAD_MB`, `MAX_ANALYSIS_CHARS`, and `MAX_QA_CONTEXT_CHARS` bound expensive request sizes.

## Backup And Restore

Back up the Docker volume or mounted data folder containing:

- `scientia.db`, `scientia.db-wal`, and `scientia.db-shm`
- `uploads/`
- `faiss_index/`
- `generated_audio/`
- `generated_code/`
- `generated_markdown/`

For durable single-instance SQLite, take backups during low write activity or
use the SQLite backup API in a maintenance script. The free Render service has
no durable volume and therefore cannot satisfy this backup procedure.

## Scale-Out Roadmap

The current app is intentionally dependency-light. For a larger production system, migrate in this order:

1. Move SQLite to PostgreSQL and add migrations.
2. Move the in-process job manager to Redis/Celery, Cloud Tasks, or another durable queue.
3. Move uploads and generated artifacts to object storage.
4. Move API rate limiting to Redis or the API gateway.
5. Split PDF processing and retrieval indexing into worker services.
6. Add OpenTelemetry traces, Prometheus metrics, and alerting.

See `docs/SYSTEM_DESIGN.md` for architecture diagrams, data flow, tradeoffs, and failure modes.
